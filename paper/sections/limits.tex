\paragraph{Limitations.}
Appendix~\ref{sec:limits-limits} states these in full. This is a measurement of one layer, developed by the author and created in October 2026, with no comparator layer and no adaptive adversary run, on synthetic permission layouts. That no returned chunk leaked means that none lay outside the
readable set at the revision the check read, under the stated trusted computing base. It does not mean fresh, nor that
unreadable chunks leave no trace, and the detection fields of Section~\ref{sec:repair} are observables we did not measure.
The enterprise layout has 19 near-identical copies of each company document, and Qdrant's recall depends on that
layout, so these recall numbers should not be read as an estimate for an organization without such copies. Every
measurement passes through one layer, and some numbers are properties of its schema as much as of a store. No single version of the library was
evaluated throughout: the end-to-end numbers are for release 2.1.0, which has known defects, the fixes we report were tested piecemeal and not end to end, and PostgreSQL, the embedding dimension and store versions differ across experiments (Appendix~\ref{app:map}). PostgreSQL row-level security was measured only in a side run (Section~\ref{sec:qual-native}). No reported run exercised the token path or the MCP tool: the harnesses build the subject directly, so that no text can choose the subject is a design argument. We did not measure document-level security in Elasticsearch and OpenSearch, sweep the share of near-duplicate chunks or
rerun the evaluation on one release, and outside the 100\% selectivity cells we have no unfiltered baseline per store. Zero-leak bounds treat repeated cases as independent, which the design supports only in part; we apply no correction for multiple comparisons across cells. The system under test, its oracles, the
meta-tests that judge the oracles and the scripts that compute the verdicts share one source, so a misconception common to them would pass every check, a
common-mode risk that repeated runs cannot remove, and no independent party has rerun anything. Three things limit it, without removing it: the oracles were written without the library's filter code,
the vendor reproducers use only the vendors' clients, and we release outputs so that others can recompute verdicts, with the gaps listed below.

\paragraph{Ethics and disclosure.}\label{sec:limits-ethics}
The author develops \sys{}, the layer under test, at \url{https://github.com/muzakkirhussain011/wardowl}, the repository that the pull-request numbers in
this paper refer to, and this evaluation found faults in that code as well as in others' (Table~\ref{tab:conf-findings}). No human subjects took part: people, documents, ACLs and canaries are synthetic, and every store and engine ran in containers or processes we
controlled. None of our findings is a chunk returned through the layer outside the readable set at the checked revision. They can still matter for
deployments that trust a pushed-down filter without a re-check, and Chroma's crash lets any user in enough groups stop an application that passes
their groups to Chroma in local mode (Appendix~\ref{app:ethics}). The behaviors were public before we reported them (times in UTC). The campaign's Redis misses, without their cause, were on the public Actions page of its run from 2026-10-26, and Chroma's crash on a public results branch from 2026-10-29 22:48. Pull request \#167, opened 2026-10-29 16:00 and merged 2026-10-30 02:16, describes the cut on Redis and MongoDB; \#187, opened 2026-10-30 00:00, Chroma's crash; and \#188, opened 11:41, MongoDB's filter field. On 2026-10-30 we then filed reports with minimal reproducers that do not need our library:
Redis (\url{https://github.com/RediSearch/RediSearch/issues/12106}, 15:54), Chroma (\url{https://github.com/chroma-core/chroma/issues/7969},
\url{https://github.com/chroma-core/chroma/issues/7970}, 15:56), Cerbos (\url{https://github.com/cerbos/cerbos/issues/3456}, 19:15) and MongoDB (documentation
feedback, no public link). So these vendors heard after the public could have, including of a crash that users can reach and of a filter that can admit too much, filed as ordinary public issues. We found no security policy file in Chroma's repository. RediSearch's policy routes serious vulnerabilities privately; we filed publicly because the over-admission needs a value longer than 4,096 bytes and our pull request had already described it, which was our judgment, and maintainers may disagree. Our first reports to Redis, Chroma and MongoDB said the maintainers were hearing of this first, which was wrong; we corrected the three public issues on 2026-11-01, and MongoDB's form cannot be edited.
Table~\ref{tab:conf-faults} in Appendix~\ref{sec:conf-results} gives each report's status. One unexplained SpiceDB trial past its documented bound, OPA's residual negation and pgvector's plan
choice have no report. No maintainer had replied on the four public issues by 2026-11-01; on 2026-10-31 a contributor outside the project opened a pull request against the first Chroma issue (chroma-core/chroma\#7974).

\paragraph{Use of AI assistance.}\label{sec:limits-ai}
Under the author's direction, an AI coding agent produced most of the library's code, the conformance kit, the oracles, the harnesses and the analysis
scripts, drafted the pre-registrations, the evidence summaries and this text, and checked the references against primary records; the numbers audit and the
critical review cited here were run by separate instances of it. The author chose the research questions, took the decisions recorded with the
pre-registrations and reviews, and takes full responsibility for the content.

\paragraph{Reproducibility.}\label{sec:limits-repro}
The artifact is at \url{https://github.com/muzakkirhussain011/wardowl-paper-artifact}, tag \texttt{evidence-v1} \tbd{archive DOI}. It holds the source of this text as of the tag, the
pre-registrations with their dated amendments, the raw outputs with seeds and versions and, for most GitHub jobs, container image digests (X2 and X5 record image tags and server versions instead), the vendor reproducers, the Kaggle runners, and the library at the commits the runs used; \texttt{REPRODUCE.md} maps each table to its data and \texttt{evidence/ARTIFACT\_GAPS.md} lists what is missing. The main gaps: the end-to-end runs stored answers and hits at $k = 5$ only, so their recall@10, and the check of the other hits against the oracle, are printed counters; the Kaggle runs did not pin their Python dependencies; and no rebuild of the prepared corpora has been shown. Compute: about 38 hours of Kaggle sessions (two T4 GPUs or four CPUs each) and more than 140 hours of GitHub-hosted runner jobs,
listed per experiment in Appendix~\ref{app:compute}; no experiment reported here ran on a local machine. Data and model licenses are in
Appendix~\ref{app:licenses}.
